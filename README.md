# Coach23

**Agentic Endurance Coach：基于训练记录与身体恢复状态，持续跟踪、复盘和调整训练的 AI 耐力教练。**

Coach23 希望把 Strava、WHOOP 和 Suunto 的数据变成可执行的训练决策：维护长期运动员档案，围绕比赛目标制定计划，在每次训练后复盘，并根据恢复状态提出调整和主动提醒。

> 当前版本：v0.1 本地开发骨架。已跑通模拟数据到每日评审的流程，尚未连接真实运动账号、云数据库或 AI 模型。下文将产品目标与已实现能力分别说明。

## 产品起点

最初的验证场景是：以 **11 月 14 日的百公里越野跑**为目标，用一个真实运动员的备赛过程验证产品价值。

需要回答的问题包括：

- 今天的训练安排是否适合当前恢复状态？
- 实际训练与计划出现偏差后，接下来几天应如何调整？
- 如何把力量训练作为训练计划的一级对象，与跑步和恢复共同安排？
- 如何持续跟踪执行情况，在运动员没有主动提问时也能及时提醒？

比赛日期是最初的产品验证场景，不是代码中的固定配置。后续应支持不同运动员、比赛目标和训练周期。

## MVP 目标

| 能力 | 预期行为 |
| --- | --- |
| 数据汇聚 | 同步 Strava、WHOOP 和 Suunto 的可用训练与恢复数据，保留来源和时间信息 |
| 运动员档案 | 积累历史记录、个人基线、训练反应、比赛目标和计划执行情况 |
| 动态训练计划 | 围绕目标安排耐力、强度、力量与恢复训练 |
| 每日评审 | 根据最新恢复状态、近期训练和计划，提出当天的调整建议 |
| 训练后复盘 | 对比计划与实际完成情况，解释偏差，并评估后续安排 |
| 主动跟踪 | 通过定时任务或数据事件触发评审，发送有明确行动意义的提醒 |

第一阶段优先打通 **Strava + WHOOP → Athlete DB → Athlete Engine → Coach Context → AI Coach → 评审与计划调整建议**。Suunto 使用独立适配器，接入进度取决于实际 API 权限，不阻塞主流程。

## 架构方向

目标采用云端架构，部署后不依赖个人 Mac 持续开机；当前 Mac 上的版本用于开发和验证。

```text
Strava / WHOOP / Suunto
          │
          ▼
数据接入与标准化 ──→ Athlete DB（长期数据与历史）
                             │
                             ▼
                      Athlete Engine
                  （基线、负荷、恢复趋势）
                             │
                             ▼
                       Coach Context
                （目标、状态、计划、数据限制）
                             │
                             ▼
                         AI Coach
                             │
                             ▼
                  评审草稿 / 计划调整建议
                             │
                             ▼
                 确认、执行、提醒与结果回写
```

以上是目标架构，当前实现范围见下一节。

- **Athlete DB 是长期记忆。** 保存训练历史和决策依据，避免把完整历史反复塞进模型上下文。当前提供内存仓库及 Supabase 表结构草案。
- **Athlete Engine 负责计算。** 将原始记录整理成可追溯的指标和趋势；模型基于这些结果进行教练推理。
- **Coach Context 负责组织信息。** 提供版本化输入，包含必要状态与数据限制；后续加入比赛目标、计划和历史决策。
- **CoachAgent 是可替换接口。** 此前讨论的 Dot 可作为候选教练实现，具体接入方式待验证；数据层与计算层不依赖某一个模型或 Agent 平台。
- **调度负责主动触发。** 云端定时任务与数据事件将驱动每日、每周和训练后评审；MCP 可作为后续工具接口，不是运行核心链路的前提。

第一版聚焦数据与决策闭环，暂不以完整手机 App 或复杂前端为目标。计划变更先形成可审阅的建议，再进入确认与执行流程。

## 当前实现状态

| 模块 | 当前状态 |
| --- | --- |
| 本地 API 与中文调试页面 | 已实现，可在本机启动 |
| Strava / WHOOP | 返回模拟记录；真实 OAuth 和同步未实现 |
| Suunto | 共用适配器接口已预留，当前返回空记录 |
| Athlete DB | 内存仓库；支持同一来源记录重复同步去重和按运动员查询 |
| Athlete Engine | 计算含今天在内的 7 个 UTC 日历日运动时长，读取当日模拟恢复分和 HRV |
| Coach Context | 版本化上下文，明确标注模拟数据与能力限制 |
| CoachAgent | 可注入接口；当前为固定规则演示，未调用 AI 模型 |
| 每日评审 | 可由命令或本地 API 触发，输出草稿，不修改计划 |
| Supabase | 运动员、源记录、教练评审的迁移草案及按用户读取策略；尚未执行验证 |
| 自动调度、通知和真实训练计划 | 尚未实现 |

当前运动时长**不等于训练负荷**，HRV 个人基线尚未计算。恢复分为模拟输入，不是 Coach23 自行评估的结果。缺失当日恢复数据时保留未知状态；跨平台重复活动尚未合并。

## 本地启动

需要 **Node.js 22+**。当前只使用 Node.js 标准库，无第三方运行依赖，无需 `npm install` 或账号密钥。

本项目在当前 Mac 上的目录为 `~/Documents/Codex/workspace/Coach23`。该机器上 `Codex` 与 `codex` 指向同一目录。

```sh
cd ~/Documents/Codex/workspace/Coach23
npm start
```

打开 [本地调试页面](http://127.0.0.1:3023)，点击「运行每日评审」，即可查看模拟同步、指标计算、教练上下文和评审草稿。

| 命令 | 用途 |
| --- | --- |
| `npm start` | 启动本地 API 和调试页面 |
| `npm run dev` | 开发模式，文件变化后自动重启 |
| `npm run demo` | 在终端执行一次模拟每日评审 |
| `npm test` | 验证重复同步、运动员隔离、数据窗口、适配器边界与 API |
| `npm run check` | 检查 JavaScript 语法 |

如默认端口已被占用：

```sh
PORT=3024 npm start
```

当前仅从进程环境读取 `PORT`，不会自动加载 `.env`。`.env.example` 中的数据库、平台凭据与教练提供方配置是后续接入占位，当前不会启用真实连接。

## 后续开发顺序

1. **持久化与身份认证**：确认云端部署方案，实现数据库仓库和用户认证，验证数据库按用户隔离。
2. **真实数据接入**：接入 Strava / WHOOP OAuth、令牌刷新、分页同步及失败重试；确认 Suunto 接口权限。
3. **运动员状态建模**：处理跨平台活动去重、运动员本地时区、历史回填、HRV 基线与训练负荷。
4. **教练与训练计划**：接入一个实际 CoachAgent 实现，加入比赛目标、力量训练和计划记录，保存带依据的评审及调整建议。
5. **主动工作流**：部署每日、每周和训练后任务，加入计划变更确认、通知、执行跟踪及运行监控。

MVP 的验收目标是：真实数据可以持续进入数据库，教练能根据目标和近期状态形成可追溯的建议，运动员可以确认调整，并在下一次评审中看到执行结果。

## 数据与运行边界

- 本地服务仅监听 `127.0.0.1`，尚无登录认证，不应直接公开部署。
- 全部演示数据保存在内存中，重启后清空。
- 数据库迁移未应用到任何云端项目，其权限策略仍需集成验证。
- OAuth 密钥、刷新令牌和数据库服务凭据应仅保留在服务端；不要提交到仓库。
- 当前不生成真实训练处方，不自动修改计划，也不发送通知。

产品目标与验收标准见 [产品需求文档](docs/PRD.md)。更多实现细节见 [架构说明](docs/architecture.md) 和 [API 说明](docs/api-design.md)。
